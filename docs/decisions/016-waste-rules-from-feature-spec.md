# ADR-016: 낭비 탐지 기준을 기능명세서(F05)에 맞춤

- 상태: 제안 (2026-11-05, 이슈 #39). ADR-010의 판정 기준·추천 타입 부분을 대체한다 (구간·카탈로그·조언만 한다는 원칙은 그대로)

## 배경
- 하네스 기능명세서 `plan/06-기능명세서.md` F05(2026-11-05)가 판정·추천 기준을 정했다.
  과다 사양 = 평균 CPU 10% 미만 그리고 P95 40% 미만, 유휴 = 최대 CPU 5% 미만 그리고 네트워크 하루 5MB 미만,
  추천 타입 = 바꾼 뒤 예상 P95(현재 P95 × 현재 vCPU ÷ 새 vCPU)가 새 타입 기본 성능 이하인 타입 중 가장 싼 것, 추천 이유 한 줄,
  메모리가 줄면 "직접 확인 필요", 목록 정렬(절감액·현재 비용·사용률·이름).
- ADR-010은 "P95 10% 미만 → 메모리 절반 t3 하나"였다. 기본 성능을 넘는 타입을 추천할 수 있었고, 왜 그 타입인지 설명이 없었다.

## 결정
- 판정은 명세 그대로 둔다. 기본 성능은 AWS가 공개한 t3·t3a vCPU당 값(nano 5 · micro 10 · small·medium 20 · large 30 · xlarge·2xlarge 40%)을
  `InstanceSpecs`에 고정한다.
- 후보는 t3 패밀리 중 **메모리가 지금의 절반 이상**인 타입으로 제한한다. 명세는 "가장 싼 것"만 말하지만, 메모리는 볼 수 없어서
  제한이 없으면 8GiB 서버에 0.5GiB(t3.nano)를 추천할 수 있다. 명세 예시(m5.large P95 9% → t3.medium)와도 이 제한이 맞는다.
- 정렬의 "현재 비용"은 목록에 보이는 월 추정 비용(최근 14일 → 730시간 환산)으로 정렬한다 (이번 달 실제 누계와 다를 수 있다).
- GPU 타입과 `InstanceSpecs`에 없는 타입은 판단하지 않는다(유휴·과다 사양 모두). 사양표에 없으면 GPU인지 알 수 없어서다.
  예상 P95와 기본 성능은 반올림 전 값으로 비교한다 (표시만 소수 첫째 자리).
- 팀 벤치마킹(F07-1)의 과다 사양 비율은 비교 자료와 같은 정의(P95 10% 미만)를 그대로 쓴다. 판단 대상(24시간 이상 켜짐 등)만 낭비 탐지와 같다.

## 결과
- 추천마다 `reason`과 `memoryCheckNeeded`가 붙어 화면이 계산 근거를 그대로 보여 줄 수 있다.
- 메모리 절반 제한은 명세에 없는 가정이라 팀 확인이 필요하다. 바꾸려면 `InstanceSpecs.downsizeCandidates`만 고치면 된다.
- 체험 모드는 단가 카탈로그에 있는 t3(micro·small·medium·large)만 후보가 된다.
