# ADR-007: 연결 이름 · 연결 삭제 · 목록 정리

- 상태: 제안 (2026-10-30, 이슈 #15)

## 배경
- 테스트 사용자가 목록에서 버려진 "대기 중" 연결 여러 개, 리전 코드, 12자리 계정 ID만 보고 어느 연결인지 구분하지 못했다.
  연결에 이름을 붙이거나, 잘못 시작한 연결을 취소·삭제할 방법도 없었다.
- CloudCost Insight는 READ ONLY다. 고객 계정의 스택(Role)을 지우는 것은 쓰기 작업이라 우리가 할 수 없다.

## 결정
- 연결 이름 `alias`(선택, 40자, 앞뒤 공백 제거)를 `aws_accounts`에 둔다 (V5). 화면 표시용이라 AWS에는 보내지 않는다.
- `DELETE /aws/accounts/{id}`는 **하드 삭제**다. 연결과 인스턴스·시간별 사용량·수집 기록을 owner 조건으로 한 트랜잭션에서 지운다.
  보관용 "삭제됨" 상태는 만들지 않는다 (다시 연결하면 새 연결이고, 남겨 둘 이유가 없다).
- 고객 스택은 건드리지 않는다. 검증된 적 있고 스택 삭제 신호를 받지 않은 연결이면 응답 `awsCleanupNeeded: true`와
  "CloudFormation에서 `CloudCostInsight-xxxxxxxx` 스택을 삭제하세요" 안내를 돌려준다.
- 삭제 뒤 늦게 온 스택 신호는 연결을 찾지 못한다. Delete는 SUCCESS(고객 스택 삭제를 막지 않음), Create/Update는 FAILED(스택 롤백 → Role이 남지 않음).
- 연결 저장을 `add`(신규)와 `save`(갱신, 없으면 아무것도 안 함)로 나눠, 진행 중이던 수집·신호 처리가 지운 연결을 되살리지 않게 한다.
- 목록은 기본으로 시작한 지 1시간 넘게 PENDING인 연결을 숨긴다(`includePending=true`면 모두). 지우지는 않는다.
- 목록 항목에 한국어 리전 이름 `regionLabel`과 스택 이름 `stackName`을 넣는다.

## 결과
- 사용자가 목록을 스스로 정리할 수 있고, 남의 연결은 404라 지울 수 없다.
- 삭제는 되돌릴 수 없다. 화면은 확인 창을 띄운다.
- 우리 쪽 삭제만으로는 고객 Role이 남는다. 다만 Trust Policy의 External ID가 지운 연결 것이라 우리도 다시 쓰지 않는다.
- 삭제와 같은 순간에 수집이 돌고 있으면 그 요청은 실패할 수 있다(인스턴스 저장 시 FK 위반). 드문 경우라 받아들인다.
