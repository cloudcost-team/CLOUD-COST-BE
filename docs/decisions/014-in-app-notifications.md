# ADR-014: 서비스 안 알림과 조회 시점 평가

- 상태: 제안 (2026-11-05, 이슈 #35)

## 배경
- S14는 예산 80·100·120%, 비용 급증, 주간 요약을 알려 준다. 팀 결정으로 **외부 채널(Slack·Discord Webhook, 이메일, 푸시)은 쓰지 않고**
  서비스 안 알림창(헤더 벨·알림 목록)만 둔다.
- 예약(자동) 수집도 하지 않는다 (ADR-002: 조회할 때 수집). 따라서 알림 조건을 확인할 시점도 사용자가 접속했을 때뿐이다.

## 결정
- 알림 목록(`GET /notifications`)과 안 읽은 수(`GET /notifications/unread-count`)를 조회할 때 연결마다 조건을 평가한다.
  기존 계산(대시보드의 `thresholdReached`·`latestSpike`, 일별 비용)을 그대로 쓰므로 수집 캐시(인스턴스 10분, CloudWatch 1시간)도 같다.
- 같은 일은 한 번만 알린다: `notifications (owner_id, event_key)` UNIQUE. 키는 예산 = 연결·월·기준, 급증 = 연결·급증일, 주간 요약 = 연결·주(월~일 KST).
  알림마다 따로 커밋하고, 동시에 만들다 UNIQUE에 걸리면 이미 있는 것으로 본다.
- 예산은 넘은 기준 이하에서 **켜 둔 가장 높은 기준 하나**만 만든다 (80→120으로 뛰면 120 하나).
- 문구는 만들 때 정해 저장한다 (금액은 그때의 원화 환율). 나중에 환율이 바뀌어도 알림 내용은 그대로다.
- 수집할 수 없는 연결·AWS 오류 연결은 그 조회에서 건너뛴다. 알림 조회가 연결 하나 때문에 실패하지 않게 한다.
- 조건 on/off는 owner별 `alert_settings`(행이 없으면 모두 켜짐). S14 저장은 조건과 연결별 예산을 한 번에 받고, 남의 연결이 섞이면 아무것도 바꾸지 않는다.

## 결과
- 접속하지 않은 동안에는 알림이 생기지 않는다 (예: 주말 동안 예산을 넘어도 월요일 첫 접속 때 알림). 응답 `notes`로 안내한다.
- 헤더 벨을 자주 부르면 매번 연결 수만큼 대시보드 계산을 한다 (DB 조회 위주, AWS 호출은 캐시). 느려지면 owner별 평가 간격을 두는 것을 검토한다.
- 나중에 외부 채널을 붙이려면 같은 `notifications` 행을 보내는 쪽만 추가하면 된다.
