# ADR-013: 팀 벤치마킹 비교 기준과 계산

- 상태: 결정 (2026-11-05 팀이 Azure 자료를 참고용으로 쓰기로 함, 이슈 #33)

## 배경
- S09는 "비슷한 규모 팀과 비교해 우리가 어디쯤인지"를 보여 준다. 비교하려면 외부 자료가 필요하고, 고객 권한은 EC2·CloudWatch 읽기뿐이다.
- 후보 자료: Azure Public Dataset V2(기획서: VM 3~20대 구독 2,607곳의 과다 사양 VM 비율 평균 42%·중앙값 35%),
  Flexera 2026 State of the Cloud(낭비 비율 평균 29%), SpendArk 2026(1~10명 팀 월 $100~$500).
- 서버별 CPU 사용률을 공개한 원본은 Azure Public Dataset이 사실상 유일하다 (AWS는 공개하지 않고, Compute Optimizer는 자기 계정 수치뿐이며 권한 밖).
  단, 마이크로소프트 내부 서비스 VM 기록이고 5분 최대값의 P95라서 우리(1시간 평균의 P95)와 대상·측정 방식이 다르다.

## 결정
- 비교 숫자는 코드가 아니라 **교체 가능한 JSON 파일**(`classpath:benchmark/reference.json`, `CCI_BENCHMARK_REFERENCE`로 교체)에 둔다.
  자료를 바꾸거나 빼기로 하면 파일만 고친다. 형식이 맞지 않으면 시작할 때 실패한다.
- ① 과다 사양 비율 = 최근 14일 중 CPU 기록이 24시간 이상인 서버 중 CPU P95 < 10% 비율 (낭비 탐지와 같은 구간·판단 대상.
  기준은 비교 자료와 같은 P95 10% 미만이라 낭비 탐지의 과다 사양 기준(ADR-016)과 다르다). 기록 14일 미만이면 `INSUFFICIENT_HISTORY`.
- 비교 자료는 **서버(VM) 대수 구간별**로 둔다 (기본 1~2대·3~20대). 사용자는 대부분 서버 1~3대인 학생 팀이라 3대 이상만 비교하면
  거의 비교되지 않고, 규모가 다른 자료와 견주면 의미가 없어서다. 판단한 서버 수로 구간을 고르고, `sizeBand`로 다른 구간도 골라 볼 수 있다.
  구간 자료가 없으면(아직 원본에서 계산 전) 비교하지 않는다(`NOT_COMPARABLE`). 팀 인원·업무 형태는 받지 않는다 (서버 대수가 비용과 더 직접 이어진다).
- "우리보다 효율적인 팀 %"는 백분위 표에서 비율이 우리보다 확실히 낮은 가장 큰 백분위다(5% 단위 하한). 1~2대 팀은 비율이 0·50·100%뿐이라
  직선 보간하면 0%인 팀에도 "더 효율적인 팀 5%"가 나와서다. **평균·중앙값만으로 분포를 지어내지 않는다.** 표가 없으면 null + 안내.
- ② 전체 낭비 비율은 볼륨·스냅샷·IP·로드밸런서를 볼 수 없어 계산하지 않는다(`UNAVAILABLE`). 권한을 늘리지 않는다 (CLAUDE.md §0).
- ③ 월 지출은 **같은 서버 대수 구간 팀들과 한 달 사용량(vCPU-시간)으로 순위를 매긴다** (2026-11-12 변경. 이전에는 SpendArk 2026
  "1~10명 팀 월 $100~$500" 한 범위와 견줘 규모가 반영되지 않았다).
  - Azure 원본에는 가격이 없고 코어 수도 구간(2·4·8·24·24 초과)뿐이라, AWS 단가로 바꾸면 계열 가정에 따라 금액이 2~4배 달라진다.
    그래서 금액이 아니라 사용량으로 견주고, 우리 팀도 같은 코어 구간 규칙으로 잰다. 양쪽에 같은 환산을 쓰므로 **단가 가정이 순위를 바꾸지 않는다**.
  - 원본 계산(`scripts/benchmark/AzureSpend.java`): 구독마다 1시간 이상 켜진 VM의 vCPU × 켜진 시간을 30일 창 안에서 더한다. 기록 끝 칸(5분 간격)까지
    켜진 VM은 30일 내내 켜진 것으로 본다 (그러지 않으면 한 달 내내 켜진 2vCPU 1대가 1,439.7이 되어 같은 조건의 우리 1,440보다 "적게 쓴 팀"으로 잡힌다).
    2026-11-12 결과: 1~2대 구독 1,446곳 중앙값 1,440, 3~20대 2,673곳 중앙값 11,520 vCPU-시간.
  - 우리 사용량 = 최근 14일(①과 같은 구간) 켜진 시간 × 코어 구간 vCPU를 30일로 환산. 기록 14일 미만이면 순위를 매기지 않고 금액만 보여 준다.
  - 화면의 일반 범위는 같은 규모 팀의 25~75번째 백분위 사용량을 **우리 팀의 vCPU-시간당 비용**으로 환산한 금액이다.
  - 비교 대상이 마이크로소프트 내부 서비스 구독이라 학생 팀과 운영 방식이 다를 수 있고, 이 차이는 보정할 방법이 없다. ①과 같이 참고용으로 밝힌다.
  - 월말 예상(EC2 온디맨드 추정, USD)이라 EBS·전송 비용이 빠져 실제보다 작다는 안내를 붙인다.
- 추천 id를 주면 시뮬레이터(ADR-012, 증가율 0)와 같은 계산으로 적용 후 위치를 준다. 사양 변경 추천을 적용한 서버는 적정,
  중지 추천을 적용한 서버는 판단 대상에서 뺀다고 가정한다.
- Azure 자료는 **참고용**으로 쓴다. 화면 설명·안내에 대상(마이크로소프트 내부 VM)과 측정 방식 차이를 밝힌다.
  기준 숫자는 원본에서 `scripts/benchmark/AzureOversized.java`(JDK만 있으면 빌드 없이 `java`로 실행)로 계산해 넣는다 (같은 원본이면 누구나 같은 숫자를 얻는다).
  2026-11-05 원본(VM 2,695,548대·구독 6,687곳)으로 계산: 1~2대 구독 1,473곳 평균 47%·중앙값 50%, 3~20대 2,622곳 평균 42%·중앙값 33%.
  기획서 값(2,607곳·42%·35%)과 거의 같아 그 값도 확인됐다. 같은 계산을 파이썬으로 따로 돌려 같은 결과를 확인했다.

## 결과
- 팀이 Azure 자료를 쓰지 않기로 하면 `oversized` 항목을 다른 자료로 바꾸거나, 화면에서 비교 영역을 숨겨야 한다 (API 형식은 그대로).
- 백분위 표를 구하면 파일의 `percentiles`에 `{ "percentile": 50, "ratioPercent": 35 }` 형식으로 넣으면 된다. 두 값은 0~100이고 위에서 아래로 줄지 않아야 하며, 어기면 시작할 때 실패한다.
